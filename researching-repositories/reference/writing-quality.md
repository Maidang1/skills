# 写作质量与反 AI 味协议

这份协议用于最终成书前的改稿。目标不是让文章更“文学”，而是让读者真正抓住仓库的作用、主线、模块重点和设计理念。

## 好文章的判断标准

读者读完后应该能回答：

1. 这个仓库为什么存在？它的核心问题是什么？
2. 它最重要的设计理念或取舍是什么？
3. 哪条主流程最能代表它的工作方式？
4. 哪些模块是必须掌握的？为什么？
5. 如果要修改或重写最小版本，应该先抓哪些抽象和测试？

如果读者只能复述目录和职责，文章不合格。

## 反 AI 味重写规则

| AI 味症状 | 重写方式 |
| --- | --- |
| “该模块主要负责处理 X” | 改成“没有这个模块，主流程会在哪里断；它把 X 问题拆成哪些状态/类型/步骤” |
| 每个模块同等篇幅 | 按 P0/P1/P2 调整篇幅，明确为什么某些模块只放附录 |
| 泛泛说“提高扩展性” | 指出具体扩展点、调用边界、配置入口和代价 |
| 只有调用链 | 补设计意图：为什么这样分层，哪里共享，哪里分叉 |
| 概念太顺滑 | 加入边界、失败模式、反例和测试保护 |
| 总结像 README | 回到仓库 thesis，写读者应带走的判断 |

## 每章的语气要求

- 先给判断，再给证据。
- 使用具体模块名、符号名、流程名，不写可替换到任何项目的句子。
- 解释困难概念，不删除困难概念。
- 明确主次：哪些必须掌握，哪些可以跳过。
- 避免“此外、同时、另外”堆列表；用因果关系串起来。

## Thesis 贯穿检查

每章完成后问：

1. 本章如何支撑或修正仓库 thesis？
2. 本章和上一章、下一章是什么关系？
3. 本章解释的是运行流程、模块架构、测试语义、设计取舍，还是 demo 裁剪？
4. 如果删掉本章，读者会失去什么关键理解？

答不出来时，章节可能只是资料堆叠。

## 章节开头模板

可以用这个轻量结构，但不要机械套用：

```markdown
## 本章要解决的问题

读这个模块前，先记住一个判断：<具体判断>。

这个判断来自三个证据：

1. `<path#symbol>` 显示 <事实>。
2. `<path#test>` 定义 <行为边界>。
3. `<flow/diagram>` 说明 <协作关系>。
```

## 章节结尾模板

每章结尾用“掌握检查”收束：

```markdown
## 掌握检查

读完本章，你应该能回答：

1. <和 thesis 相关的问题>
2. <和模块边界相关的问题>
3. <和修改/测试相关的问题>

如果要继续深入，下一章应该读 `<chapter>`，因为 <因果关系>。
```

## 禁止句式

以下句式不是绝对不能出现，但出现后必须立刻接具体机制，否则视为 AI 味：

- “主要负责……”
- “提供了一套……”
- “提高了可维护性/扩展性/灵活性……”
- “通过模块化设计……”
- “整体架构清晰……”
- “方便用户……”
- “核心逻辑位于……”

更好的写法是：

- “这个模块把 `<输入>` 转成 `<中间状态>`，再交给 `<下游模块>`；分叉点在 `<symbol>`。”
- “扩展性来自 `<registry/config/hook>`，代价是 `<复杂度/约束>`。”
- “如果修改 `<行为>`，至少要回归 `<test>`，因为它定义了 `<语义>`。”

## 最终 Anti-AI Pass

成书前逐章标记：

| 检查项 | 通过标准 |
| --- | --- |
| 主线 | 每章都能回到仓库 thesis 或明确说明是支撑章节 |
| 重点 | P0/P1/P2 篇幅有差异，不平均铺陈 |
| 证据 | 关键判断有 S1/S2 证据 |
| 图示 | 图不是目录树，能解释流程、边界或分叉 |
| 深度 | 至少讲到机制层；P0 模块讲到取舍层和修改层 |
| 初学者路径 | 有术语解释和阅读顺序，但不删除复杂概念 |

任一 P0 章节失败，返回重写。
